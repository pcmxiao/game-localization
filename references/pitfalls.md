# 踩坑清单

每一条都是真的坏过一次或白干一次。多数是「静默失败」—— 不报错，只是结果不对。

## 判据类

### 假名检测会骗你
用 `[぀-ゟ゠-ヿ]` 判断「还没翻」会漏掉**全汉字的外语词**：勉強、料理、元気、statistics。
反过来目标语言里合法的东西会误报：中文间隔号「李·爱铃」、日文长音符「ーーー」、
有意保留的角色原名。

**唯一可靠的判据：与原始备份同路径下完全一致。**
字符集检测只能当粗筛或分诊旁证。

### 「残留 N 条」不等于「漏翻 N 条」
实测：扫出 73 条残留，核实后**只有 35 条是真漏翻**，其余是保留的原名 10 条、
道具名前缀 14 条、中点 10 条、长音符 4 条。
**逐条核实再下结论**，否则会去补根本不需要补的东西。

### 扫描脚本自己也会骗你
自写的扫描脚本里 `texts_map(data)` 忘传 `data["events"]`，
139 张地图全部返回「0 条可见文本」。**看起来是「全部翻完了」，其实是「一个都没扫」。**

→ 教训：任何统计脚本都要先在**已知非空**的样本上验证。比如先确认某张已知地图
应该返回 991 条。

### 审计范围和抽取范围不一致 = 荒唐报告
第一版 `audit.py` 自己遍历整棵 JSON 树，结果把 `note` 注释、事件名、插件参数、
`.meta` 的 GUID 全算进来，报告「481,257 条没翻」。

→ **审计必须调用抽取器**。「哪些算玩家可见」只有一个定义，抽取和审计共用。

### 备份找不到时，审计会给一份「假全清」
`backup_dir()` 产出的是 `<dest>/<tag>_<时间戳>/<原名>/`。
审计脚本一开始只往下探**一层**，而且要求候选目录**直接**含 `.json`。

用户把 `gameloc_backups/` 父目录传进来（很自然 —— release.md 就是这么描述备份位置的），
探测不触发 → 备份抽出 **0 条** → 所有条目都走 `orig is None` 分支 →
全部归到「新增条目」→ 报告显示 `✓ 已改动 0` → **退出码 0**。

一份看起来通过的、完全无意义的报告，比报错危险得多。

→ 两条一起上：
1. 递归向下探测，直到找到真正含数据文件的目录（时间戳目录、父目录、数据目录都能接受）
2. **「当前有条目、备份抽出 0 条」直接硬报错**，返回非零 —— 静默的零永远不是「通过」

### 25,000 条「一致」里 97% 不用管
`audit.py` 刚跑对时，25,175 条「与原文完全一致」把人头都看麻了 —— 其中
24,627 条是纯 ASCII 资源标识符（`s_TVkun`、`actor1`），3 条是裸控制码。

→ 加一层自动分诊：纯 ASCII 标识符 / 裸控制码 / 空串 → 排除；
中日同字（`夏乃`、`静`、`生气`）和含假名的 → 留给人工。25,175 → 545。

## 写入类

### `set_path` 的正则陷阱
```python
re.findall(r'([^\[\]]+)|\[(\d+)\]', path)
```
对 `terms.messages.autosave` 会得到单个 `"terms.messages.autosave"`，
然后在根字典建了这个键。**JSON 依然合法**，不抛异常，不报错。

→ **路径不存在就抛异常**。宁可吵一点。

### 键名里含点号 → 路径有歧义，会静默写错位置
路径用 `.` 分隔，所以键名本身的 `.` 无法表达。最坏的情况是**两种解释同时存在**：

```json
{"ui": {"title": "嵌套值"}, "ui.title": "扁平值"}
```

`set_path(obj, "ui.title", ...)` 会写到**嵌套**那个，
扁平的 `ui.title` 一个字节没动，而且不报错。

更常见的是扁平本地化表（`menu.title`、`ui.button.label`）整条抽不到 ——
白名单按整串匹配时，`menu.title` 不等于 `title`，直接被跳过。

→ 键名用 `escape_path_token()` 编码：`.` → `\.`，`[` → `\[`，`]` → `\]`。
抽取器拼 path 时一律走它；`parse_path` 负责还原。
白名单改成按**最后一段**匹配，`menu.title` 才收得到。

### 控制码改错 = 崩
- 冻结：`\V[n]` → `[[R0]]` → 还原
- 实测频次（某 RPG Maker MZ 游戏）：`\m[n]` 18427 · `\z[n]` 18427 ·
  `\N[n]` 5580 · `\ac\…\}` 709 · `\V[n]` 501 · `\item[n]` 363 ·
  `\{` `}` 131/15 · `\^` 3 · `\C` 1 · `\G` 1，外加 `%1 %2 %3`

合计 44,158 处，其中 `\m` + `\z` 占 **83%**。通用工具只保护 `\V \C \N \I`，
翻这批必崩。

等值校验器要检查**冻结占位符的多重集完全相等**，不只是「大概有」。
它真的拦住了手写译文里 2 处漏写和多写。

### 写完必须回读
不信返回值。写完重新 `json.load`，逐条 diff 目标路径。
路径写错、层级写错、类型写错，只有 diff 看得出来。

### 「绝不写部分补丁」必须是代码保证，不能只是注释
`apply_sheet.py` 的 docstring 一开始就写着「任何一步失败都中止整批」，
但实现是**边检边写**：第 3 行的 src 对不上时，第 1 行早就落盘了。
于是同一次运行既写了东西、又报了失败 —— 半张补丁，比完全没写更难查。

→ 校验和写入必须**分成两遍**：先整批预检（只读，不落盘），
全过了再写。这样「原子」才是真的，而不是一句愿望。

### 退出码要能区分「表填错了」和「文件被改坏了」
旧实现把「预检失败的行」和「回读 diff 不一致」都算成同一类，
都返回 5。但这两件事的危险程度差一个量级：

- **回读不一致** → 写进去的和预期不同，文件可能已经损坏，**立刻从备份恢复**
- **预检失败** → 一个字节都没写，只是表要改，重新填再跑即可

混在一起，CI 和脚本调用方就没法判断该不该报警。

→ 分开：`5` 回读不一致（危险）· `6` 预检失败未写入（安全）· `7` 写入/回读阶段失败。

### 用 `r["id"]` 做行过滤，id 一空就全军覆没
排除「控制码不匹配」的行时，实现是：
```python
bad_ids = {r["id"] for r, _ in bad_esc}
good = [r for r in rows if r["id"] not in bad_ids]
```
用户从 Excel 粘贴时很容易把 `id` 列冲掉。id 一空，`bad_ids` 就成了 `{""}`，
于是**所有** id 为空的行都被一起丢掉 —— 一行控制码写坏，连累整张表的好行
静默不写，还返回 0。

→ 按**对象身份**排除（`id(r)`），不要按某个可能为空的字段值排除。

### 幂等重跑不能被当成冲突
写完一次再跑同一张表，游戏里存的已经是**译文**，此时 `src` 天然对不上。
若预检只比对 `src`，第二次跑就会报「原文对不上」而整批中止 ——
把「幂等」错杀成「冲突」。

→ 先判「现值 == 译文」，是则算空操作跳过，**再**去核对 `src`。

## 流程类

### Excel 粘贴会整列错位
从 Excel/WPS 复制译文贴回 CSV，两行被并成一格，后面的内容整体平移一位。

实测两批都中招，而且**粘贴后肉眼看不出来**。

→ 每次填完先 `--dry`。校验器按控制码逐行比对，能精确定位到第几行。

### 别用文本字符串做映射键
同一句「うん」在游戏里出现几十次。按文本映射回去会因空白/转写差异翻车。

→ 先去重，按**去重编号**建映射，再按编号回填到所有出现处。

### 长列表翻译完要抽查首尾和重复段
自己写重复段落时把第 172 行写成了半句，且 177/178 漏抄原文。
写完一次目视扫描就发现了。

→ 翻译完长列表，随机抽 5% 复读，特别是**首、尾、重复段**。

### 回复里贴的内容必须从文件读
贴「游戏内实际内容」时凭记忆粘贴，混进了另一个批次的行 —— 展示的和实际写入的不符。

→ 写脚本按 path 从 JSON 读取后再展示。

## 内容策略类

### 词组 vs 词根
`メイク`（化妆）含 `イク`、`メッセージ`（留言）含 `セー`。
用词根筛敏感内容会满屏误报。

→ **筛查用完整词组**，不要拆成词根。用真实项目的词表，
里面写的是完整词形，命中就是命中。

### 正则的 alternative 必须清洗
筛查正则里塞了含空格或非目标语言的 alternative，
`pattern.search()` 匹配到**空串**，498 行全部假阳性。

→ alternative 逐个 `strip()`，剔除非目标语言字符。
写完立刻用已知正例/负例各测几条。

## 编码与输出类

### 读和写是两个独立决定
用同一套编码假设读写会静默毁掉译文。日文 Shift-JIS 装不下中文/西里尔/阿拉伯文，
硬塞会静默替换成 `&#xxxx;`。

→ 读编码、写编码分开配置；写默认 UTF-8，除非有明确理由。

### 输出编码：控制台 + 管道
Windows 控制台默认 GBK。脚本 `print` 一个 `✔` 就 `UnicodeEncodeError`。
危险的不是报错本身 —— 是**报错之前已经打出来的那部分是乱码**，
排查时容易误判成数据坏了。

光靠 `sys.stdout.reconfigure(encoding="utf-8")` 不够：Python 吐 UTF-8 字节，
控制台仍按 GBK 解码，整篇变乱码；管道（`|`、`>`）还会再重编码一次。

→ 脚本里统一调用 `setup_stdio()`：先 `SetConsoleOutputCP(65001)` 再 reconfigure。
→ 需要长期保存的输出用工具自带的 `--report out.json`（写 UTF-8 文件），
不要靠重定向命令行输出。

## 小函数类

### 漏一个 `return`
`visible_texts()` 忘了 `return out`，静默返回 `None`，
配 `or []` 后不报错但恒为空。整条流水线跟着失效。

→ **小函数一定要测非空场景。**
